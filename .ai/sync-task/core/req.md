# 同步任务模块需求开发文档

## 1. 文档定位

本文档是 DolphinScheduler 二开“同步任务”模块的需求开发基线文档，用于统一产品、交互、前后端实现和测试验收口径。

后续正确协作方式应调整为：

1. 先在本文件中梳理、修改和确认需求。
2. 再依据需求文档补产品原型或交互草案。
3. 最后按确认后的文档实施开发、自测和交付。

本文件后续将作为同步任务模块的“唯一需求主文档”。用户后续若调整想法，应优先修改本文档，再进入开发阶段。

## 2. 背景与目标

### 2.1 项目背景

当前项目基于 Apache DolphinScheduler 进行二次开发，目标不是重写调度平台，而是在其现有项目、数据源、工作流、定时、实例和权限体系内，新增一套更成熟的数据同步任务配置能力。

SeaTunnel 在本方案中的定位是“同步执行引擎”，而非独立产品界面。用户不应直接手写 SeaTunnel 配置，而应通过 DolphinScheduler 内的页面化向导完成同步任务定义。

### 2.2 业务目标

构建一个可在 DolphinScheduler 中直接使用的数据同步任务工作台，使用户能够完成以下完整业务链路：

1. 选择同步任务所属项目。
2. 选择源端数据源、数据库、表。
3. 选择目标端数据源、数据库、Schema、表名。
4. 配置同步方案：字段映射、源端过滤条件、数据去向和预留数据处理。
5. 预览并确认目标端建表 SQL。
6. 自动生成并可编辑 SeaTunnel 配置。
7. 保存为 DolphinScheduler 工作流。
8. 立即执行或配置周期调度。
9. 查看实例执行状态、任务节点状态和同步数据量。

### 2.3 产品目标

同步任务页面要尽量接近成熟数据集成产品的使用方式，重点参考以下产品的交互思路：

- 阿里云 DataWorks 数据集成
- Azure Data Factory Copy / Data Flow
- Airbyte Connections
- 云厂商大数据平台的数据集成与调度产品

目标不是照抄视觉，而是学习这些成熟产品在以下方面的处理：

- 步骤式流程拆分
- 源端与目标端分区表达
- 字段设计与映射的可读性
- DDL 与配置预览的工作台化呈现
- 执行状态反馈的清晰度

## 3. 产品范围

### 3.1 本期必须覆盖

- DolphinScheduler 菜单新增“同步任务”入口
- `/ui/sync-task` 四步向导页面
- 数据源 / 库 / 表 / 字段读取
- MySQL / PostgreSQL / Oracle / Doris 单表同步配置；Doris 按 MySQL 协议连接，但作为独立目标类型处理 DDL 和类型映射
- 字段勾选与目标字段设计
- 拖拽连线映射
- 目标建表 DDL 预览与确认执行
- SeaTunnel 配置生成、预览、编辑
- 保存同步任务为 DolphinScheduler 工作流
- 工作流上线与实例启动
- 周期调度配置
- 执行结果与数据量展示

### 3.2 本期不做

- 脱离 DolphinScheduler 的独立同步平台
- 用户手工编写完整 SeaTunnel 配置文件作为主流程
- 脱离现有数据源体系重新维护独立连接管理
- 破坏 DolphinScheduler 原有工作流定义、定时、运行实例页的行为

## 4. 用户角色与典型使用者

### 4.1 主要用户角色

- 数据开发工程师
- 数据集成开发工程师
- 调度平台管理员

### 4.2 用户特征

这类用户通常熟悉：

- 数据源概念
- 库、表、字段、主键、可空等元数据概念
- 调度任务和周期运行

但他们不希望：

- 手工拼 SeaTunnel 配置
- 手工写复杂 cron 表达式
- 在一个页面上面对大量无结构配置项
- 保存并执行后不知道发生了什么

## 5. 总体产品原则

### 5.1 平台复用原则

- 同步任务必须复用 DolphinScheduler 现有项目体系。
- 同步任务必须复用 DolphinScheduler 现有工作流定义能力。
- 同步任务必须复用 DolphinScheduler 现有实例运行与查看能力。
- 周期调度能力应尽量复用 DolphinScheduler 原生定时交互方式。

### 5.2 原生功能保护原则

- 不得破坏原有工作流定义页右侧“定时”功能。
- 不得污染 Dolphin 原生工作流和同步任务的配置边界。
- 同步任务需要的特殊逻辑，应尽量限制在同步任务模块内部实现。

### 5.3 产品体验原则

- 页面应使用向导式步骤拆分，避免把所有配置平铺展示。
- 文案必须有信息价值，避免“空话”“废话”“解释性垃圾文案”。
- 页面上的提示文案要服务于操作，而不是占空间。
- 用户完成一步后，下一步该做什么必须清晰。
- 成功或失败状态必须明确反馈，并且能给出下一步动作。

### 5.4 交付方式原则

- 后续所有改动应先更新需求文档，再进入代码开发。
- 开发完成后必须做模拟人类逐步点击页面的真实自测。
- 不能再采用“用户口头说一句 -> 直接改代码 -> 用户再试错”的方式作为主流程。

## 6. 业务流程总览

同步任务的标准业务流程如下：

1. 用户进入同步任务页面。
2. 选择归属项目。
3. 选择源数据源、源数据库、源表。
4. 选择目标数据源、目标数据库、目标 Schema、目标表名。
5. 进入字段设计，勾选需要同步的源字段。
6. 系统基于勾选结果生成目标字段草稿。
7. 用户调整目标字段名、类型、注释、主键、可空属性。
8. 用户通过拖拽连线或自动映射确认源字段与目标字段对应关系。
9. 用户预览目标端建表 DDL，并按需编辑。
10. 用户点击“确认建表”后，系统在目标端执行建表。
11. 用户查看全局配置预览，必要时编辑 SeaTunnel 配置。
12. 用户保存同步任务，系统生成或更新 DolphinScheduler 工作流定义。
13. 用户选择立即执行或周期调度。
14. 若立即执行，系统自动上线并启动实例。
15. 若周期调度，系统保存工作流并配置调度策略。
16. 页面显示当前任务提交状态、实例状态、节点状态和同步数据量。

## 7. 页面信息架构

### 7.1 页面入口

- 导航位置：DolphinScheduler 菜单栏，“源中心”右侧
- 页面路由：`/ui/sync-task`

### 7.2 页面结构

页面采用四步向导结构：

| 步骤 | 名称 | 核心目标 |
|------|------|----------|
| 1 | 选择源与目标 | 确认项目、源端、目标端基础连接信息 |
| 2 | 配置同步方案 | 完成字段映射、源端过滤条件、数据去向和预留数据处理配置 |
| 3 | 执行与调度 | 预览建表 SQL、执行建表、配置执行方式 |
| 4 | 预览与发布 | 预览配置、保存任务、执行任务、查看结果 |

### 7.3 全局公共能力

页面需要有以下全局能力：

- 全局步骤条
- 全局“查看配置预览”入口
- 上一步 / 下一步流程控制
- 统一错误提示
- 统一成功反馈

## 8. 第 1 步：选择源与目标

### 8.1 目标

完成同步任务的基础连接定义，为后续字段读取、建表和运行提供上下文。

### 8.2 界面布局要求

采用已确认的源目标对照式工作台布局：

1. 顶部轻量步骤条
2. 基础信息区：配置检查、归属项目、任务名称、同步目标
3. 同步对象工作台：左侧源端、右侧目标端、中间“对象确认”节点

要求：

- 第 1 步只确认项目、源表和目标表，不展示字段统计、表注释、预估行数等摘要卡。
- 源端与目标端分区明显，保持 `SOURCE / TARGET` 标签和连接状态。
- 中间保留“对象确认”圆形节点和上下连接线，表达源端到目标端的对象关系。
- 不展示“目标表模式”切换控件，目标表处理方式由目标表存在性自动推导。
- 不要堆多余解释文案，避免大面积空白和无意义摘要。

### 8.3 字段要求

#### 项目区

- 归属项目 `*` 必填

#### 源端区

- 数据源
- 数据库
- 数据表
- 数据源类型支持 MySQL、PostgreSQL、Oracle、Doris；Oracle 默认使用连接用户 Schema，Doris 默认使用 MySQL 协议库表元数据

#### 目标端区

- 数据源
- 数据库
- 参考表（可选）
- Schema
- 目标表名
- 目标端方言支持 MySQL、PostgreSQL、Oracle、Doris；目标字段类型、建表 SQL、主键和注释语法必须随目标端类型变化
- 目标表名填写后，系统自动检查目标表是否存在：
  - 存在：提示“使用已有表”，第 2 步按已有表字段回显并自动匹配同名字段。
  - 不存在：提示“将新建”，第 2 步按源字段生成目标字段，第 3 步生成建表 SQL。

### 8.4 交互要求

- 选择源数据源后，自动加载库列表。
- 选择源库后，自动加载表列表。
- 选择源表后，自动加载字段元数据。
- 选择目标数据源后，自动加载目标库列表。
- 选择目标参考表时，可加载参考表字段作为目标字段初始参考。
- 若用户未填写目标表名，可在选中源表后默认带出同名建议。
- 不允许用户在第 1 步手动选择“新建目标表 / 使用已有表”；该状态只能由目标表存在性检查结果决定。
- 第 1 步只负责项目、源端和目标端基础选择，不展示源端过滤条件、字段映射、数据去向或数据处理配置。
- 源端过滤条件统一放入第 2 步“配置同步方案”，避免把连接选择和同步行为配置混在一起。

### 8.5 校验规则

进入第 2 步前，第 1 步至少需要满足：

- 已选择归属项目
- 已选择源数据源
- 已选择源数据库
- 已选择源表
- 已选择目标数据源
- 已选择目标数据库
- 已填写目标表名
- 第 1 步校验摘要只提示项目、源端对象、目标端对象和目标表预检查，不提示源端过滤条件。

### 8.6 文案要求

- 只保留必要标签和占位提示
- 归属项目必须有必填标识
- 不要出现低价值提示，如“工作流归属当前项目”这类无必要标签

## 9. 第 2 步：配置同步方案

### 9.1 目标

让用户在源端和目标端已经确定后，完成真正影响同步行为的方案配置，包括字段映射、源端过滤条件、数据去向和预留数据处理。

### 9.2 总体布局

第 2 步采用模块化工作台结构：

- 左侧：模块列表
- 右侧：当前模块详情

模块顺序固定为：

1. 字段映射关系
2. 源端过滤条件
3. 数据去向
4. 数据处理

要求：

- 第 2 步名称固定为“配置同步方案”，不再叫“设计字段”。
- 左侧模块列表只展示模块名称、状态标签和短说明，不展示“1 映射 / 2 过滤 / 3 去向 / 4 处理”这类重复编号。
- 默认进入第 2 步时选中“字段映射关系”。
- 字段映射关系模块采用左右双工作台：左侧源字段区、右侧目标字段设计区、中间连线映射层。

布局应更接近成熟数据产品的字段设计工作台，而不是简单表格拼接。

当前第 2 步正式设计以原型 `../prototype/field-mapping-workbench-v4.html` 为准。正式代码实现前必须先对照该原型，不能再回退到旧版“字段名 / 当前来源 / 映射方式 / 来自 xx”样式。

### 9.3 源字段区

源字段区每行至少展示：

- 是否同步
- 源字段名
- 源字段类型
- 字段注释
- 是否主键
- 是否允许为空

要求：

- 列顺序固定为：同步、源字段、源类型、字段注释
- 主键、非空、可空标签显示在源字段名同一行后方
- 字段注释过长时单行省略，避免撑高行高
- 源字段名应靠近连线锚点，使连线从源字段区右缘发出
- 连线原点必须位于源字段区的最右边缘附近
- 不能让连线起点缩在字段内容内部
- 每个源字段都必须有连接点，包括未勾选或未映射字段

### 9.4 源字段区交互

必须支持：

- 全选
- 反选
- 清空
- 只看异常
- 单个勾选
- 部分字段勾选

说明：

- “部分字段勾选”是必须能力，不能因为全选/反选逻辑导致单个勾选失效。
- 源字段区的工具按钮必须放在源字段区内部。
- 全选、反选、清空只影响同步参与状态，不应凭空创造不合理字段映射。

### 9.5 目标字段设计区

目标字段区每行至少支持：

- 目标字段名编辑
- 目标字段类型选择
- 目标字段注释编辑
- 目标字段主键设置
- 目标字段可空设置

要求：

- 列顺序固定为：目标字段、目标类型、字段注释、主键、可空
- 目标字段使用输入框，不再额外展示重复“字段名”列
- 目标类型使用下拉选择框
- 字段注释使用输入框
- 主键、可空使用复选框，必须逐行展示
- 目标字段类型应允许用户自行选择，而不是只能沿用源类型
- 目标字段默认值应根据目标库类型进行类型推荐
- 目标字段区不需要无意义的全选、清空、反选按钮
- 目标字段区不展示“来自 xx”“当前来源”“映射方式”等文字，字段来源通过连线和图例表达
- 新建目标表模式下，目标字段区顶部展示“保持源名 / 全小写 / 全大写”，并直接作用于目标字段输入框

### 9.6 连线映射设计

#### 9.6.1 交互目标

用户可以通过拖拽连接源字段与目标字段，直观调整字段对应关系。

#### 9.6.2 基本要求

- 左侧源字段可作为连线起点
- 右侧目标字段可作为连线起点
- 左右两侧都必须支持拖拽
- 没有对应字段的数据行也必须有小圆点，便于用户自行连接
- 字段头部区域也可以作为落点，不应只允许命中极小圆点
- 映射关系变更后，连线应立即变化
- 一个源字段可以关联多个目标字段
- 一个目标字段同一时刻只能关联一个源字段
- 目标字段已有来源时，新连线替换旧来源

#### 9.6.3 视觉要求

- 连线层必须在字段面板之上
- 连线交叉时仍必须可见
- 连线样式应简洁、克制、专业
- 连接点位置要符合左右阅读习惯
- 左右连接点样式必须统一
- 自动映射使用虚线，手动拖拽映射使用实线
- 页面必须展示虚线和实线的含义说明
- 连线默认展示，不再提供显示 / 隐藏按钮

#### 9.6.4 类型兼容要求

- 用户拖拽建立映射时，系统必须判断目标字段类型是否能安全承接源字段类型。
- 允许安全扩容，例如 `INT -> BIGINT`、`VARCHAR(64) -> VARCHAR(255)`、`DATE -> TIMESTAMP`。
- 不允许可能截断或丢精度的映射，例如 `BIGINT -> INT`、`VARCHAR(255) -> VARCHAR(64)`、`TIMESTAMP -> DATE`。
- 不兼容时不建立连线、不改变原映射，并提示源类型、目标类型和失败原因。

### 9.7 自动映射与默认规则

当用户勾选源字段后，系统默认按以下规则自动生成目标字段：

1. 目标字段名默认等于源字段名
2. 目标字段类型按源类型和目标库类型推导
3. 目标字段注释默认继承源字段注释
4. 目标字段主键默认继承源字段主键信息
5. 目标字段可空默认继承源字段可空信息
6. 默认一对一自动映射

### 9.8 源端过滤条件

源端过滤条件是第 2 步“配置同步方案”中的可选模块，不在第 1 步展示。

要求：

- 不配置时表示全量读取。
- 允许用户在源表读取前配置结构化过滤条件，用于控制同步范围、时间区间和少量抽样验证。
- 源端过滤条件参考 Fivetran 的 row filtering 思路，采用“表级过滤器 + 结构化条件 + 系统拼接 WHERE”的方式，不提供自由 SQL 编辑器作为主入口。
- 源端过滤条件支持的基础类型至少包括整数、字符串、日期 / 时间和布尔。
- 源端过滤条件支持的操作符至少包括：等于、不等于、大于、小于、大于等于、小于等于、为空、不为空；字符串还应支持包含、前缀匹配和 IN。
- 单表最多支持 3 个过滤条件，超过时应提示用户收敛条件。
- “暂时同步几条数据”不作为正式同步语义，需单独作为试跑 / 预览抽样能力处理，不能污染正式同步范围配置。
- 配置预览和 SeaTunnel source query 中必须展示源端过滤条件。
- 源端过滤条件只影响 source 读取范围，不改变目标表字段结构和映射逻辑。

### 9.9 数据去向

数据去向是第 2 步“配置同步方案”中的可选模块。

要求：

- 当前只保留“同步前 SQL（custom_sql）”能力。
- 页面不展示“写入策略”入口，也不展示写入策略相关文案。
- 页面不使用 `preSql` 命名，避免误导用户以为 SeaTunnel JDBC sink 存在 `preSql` 参数。
- 当用户填写同步前 SQL 时，SeaTunnel 配置应使用 `data_save_mode = "CUSTOM_PROCESSING"` 和 `custom_sql`。
- 若当前 sink 配置使用 `query` 写入模式，且该模式会影响 `custom_sql` 执行，页面必须提示冲突或阻断保存。

### 9.10 数据处理

数据处理是第 2 步“配置同步方案”中的预留模块，本期不实现。

要求：

- 模块必须展示“暂未实现”标签。
- 模块内不展示可生效的输入控件。
- 保存、执行和 SeaTunnel 配置生成不得读取数据处理模块配置。
- 后续能力预留方向包括字符串替换、AI 辅助处理和数据向量化。

### 9.11 第 2 步校验规则

进入第 3 步前，至少要求：

- 至少勾选一个源字段
- 每个已勾选字段都具有目标字段名
- 每个已勾选字段都具有目标字段类型
- 映射关系保持可用状态
- 若配置源端过滤条件，每条启用条件都必须具备字段、操作符和值；为空 / 不为空类操作符不要求值。
- 若配置同步前 SQL，必须通过基础 SQL 安全校验，不允许多语句危险组合。

## 10. 第 3 步：执行与调度

### 10.1 目标

完成目标端建表和执行方式配置。

### 10.2 执行方式

执行方式包括：

- 立即执行
- 周期调度

不包含：

- 手动业务时间

### 10.3 立即执行

立即执行不是简单创建一个下线工作流，而应完整执行以下链路：

1. 保存工作流定义
2. 上线工作流
3. 启动工作流实例
4. 页面反馈运行状态

### 10.4 周期调度

周期调度应复用 DolphinScheduler 原生“定时”交互风格。

要求：

- 分、时、日、周、月等配置要友好表达
- 不要求用户直接写复杂 cron
- 不要破坏原生工作流定义页的定时功能
- 不要强制要求前 1、2 步全部填写完整后才能打开调度配置

### 10.5 目标端建表

#### 10.5.1 产品要求

- 页面不能提前自动创建目标表
- 必须由用户点击“确认建表”后，才真正下发 DDL

#### 10.5.2 界面要求

- 进入第 3 步后自动生成 DDL，不再要求用户点击“生成建表语句”才看到 SQL
- DDL 使用 SQL 编辑器方式展示，至少包含 SQL 高亮、行号、复制、格式化、重新生成和编辑状态
- DDL 格式化应让 `CREATE TABLE` 内字段定义一行一个字段，缩进统一；不能把字段类型内部的逗号误拆成新字段行
- 用户编辑 DDL 后展示“已手工修改”状态
- 用户确认 DDL 后点击“确认建表”

#### 10.5.3 交互要求

- 若目标表已存在，应给出明确且可理解的反馈
- 若建表失败，应明确反馈失败原因
- 若建表成功，应明确反馈成功

### 10.6 第 3 步校验策略

- 打开周期调度配置不应和字段映射完成强耦合
- 但真正执行建表前，必须保证目标字段定义完整
- 真正保存并执行前，必须保证第 1、2 步关键配置完整

## 11. 第 4 步：预览与发布

### 11.1 目标

完成最终配置审阅、任务保存、任务执行和结果反馈。

### 11.2 配置预览

配置预览应通过全局单一浮层实现，而不是在每个步骤重复放置。

要求：

- 支持查看自动生成的 SeaTunnel 配置
- 支持编辑配置
- 支持重置为自动生成结果

### 11.3 保存同步任务

“保存同步任务”用于：

- 创建或更新 DolphinScheduler 工作流定义
- 保留任务草稿
- 暂不执行任务

### 11.4 保存并执行

“保存并执行”用于：

- 保存工作流
- 上线工作流
- 启动实例
- 返回同步任务列表并回填最近运行状态

### 11.5 执行后返回列表

页面不应在第 4 步提交成功后继续停留在向导内。同步任务已经具备资产列表和详情抽屉后，执行提交成功应返回同步任务列表，避免用户误以为还需要继续在最后一步操作。

同步任务列表至少承接：

- 最近运行阶段
- 工作流编码
- 最近实例 ID
- 最近运行时间
- 同步数据量
- 失败摘要
- 编辑 / 修复入口

### 11.6 跳转策略

不跳转到 DolphinScheduler 原生实例详情页，也不继续停留在第 4 步向导。

推荐方式：

- 保存同步任务：保留在当前向导，便于继续编辑。
- 保存并执行 / 保存并启用调度：提交成功后返回同步任务列表。
- 同步任务列表和详情中继续提供查看历史、查看配置、编辑修复的入口。

### 11.7 文案要求

第 4 步必须避免这些低价值提示：

- 解释内部实现但不帮助用户决策的长句
- 成功后“空洞式恭喜文案”
- 重复说明页面不会跳转、可以查看日志这类废话

运行状态文案应短、准、可操作，例如：

- 保存中
- 提交中
- 运行中
- 执行成功
- 执行失败
- 调度已启用

## 12. 核心后端接口要求

### 12.1 数据源字段元数据接口

接口：`/datasources/tableColumnMetas`

要求返回真实字段元信息：

- 字段名
- 类型
- 注释
- 主键
- 可空

历史缺陷需要长期规避：

- 类型返回 `unknown`
- 中文注释乱码
- 枚举类型解析异常

### 12.2 目标建表预览接口

接口：`/datasources/preview-target-table`

要求：

- 根据页面目标字段设计生成 DDL
- 支持主键
- 支持字段注释
- 面向 MySQL / PostgreSQL / Oracle / Doris 时生成合理的 DDL 结构
- Oracle DDL 使用双引号和独立 `COMMENT ON COLUMN`，不使用 `CREATE TABLE IF NOT EXISTS`
- Doris DDL 使用反引号、列注释和本地单副本可执行的分桶属性

### 12.3 目标建表执行接口

接口：`/datasources/create-target-table`

要求：

- 仅在点击确认建表后执行
- 支持目标表已存在时的友好处理
- 支持返回可识别的失败原因

### 12.4 工作流保存与执行接口

关键接口包括：

- `/projects/{projectCode}/workflow-definition/query-by-name`
- `/projects/{projectCode}/workflow-definition/verify-name`
- `/projects/{projectCode}/workflow-definition`
- `/projects/{projectCode}/workflow-definition/{code}/release`
- `/projects/{projectCode}/executors/start-workflow-instance`

要求：

- 保存同步任务时支持创建或更新
- 执行时必须完成“保存 -> 上线 -> 启动实例”闭环

### 12.5 源端过滤条件生成规则

接口或配置生成阶段需要把第 2 步“源端过滤条件”模块的结构化条件纳入源表读取链路。

要求：

- 过滤条件必须来自页面的结构化配置，不得接收用户任意 SQL 片段作为主输入。
- 过滤条件应在生成 SeaTunnel 配置或等价查询约束时进入 source 读取链路。
- 若连接器支持下推，优先生成等价 WHERE / predicate 条件。
- 若连接器不支持下推，应由执行链路按统一规则在读取后过滤，但页面配置语义保持不变。
- 已有目标表场景下，源端过滤条件只影响 source 读取范围，不改变目标表字段结构和映射逻辑。

## 13. 数据与状态要求

### 13.1 数据源密码策略

源端和目标端连接凭据应复用现有数据源配置，不应要求用户在页面重复输入密码。

### 13.2 配置生成策略

SeaTunnel 配置应由页面状态自动生成，输入来源包括：

- 源端连接参数
- 目标端连接参数
- 字段映射结果
- 目标字段定义
- 调度配置

### 13.3 映射结果一致性

以下环节都必须使用“当前最新字段映射结果”：

- DDL 预览
- DDL 执行
- SeaTunnel 配置预览
- 保存工作流
- 实际运行

### 13.4 SeaTunnel 字段映射生成规则

当目标表已存在，且用户在第 2 步通过拖拽手动指定源字段与目标字段关系时，SeaTunnel 配置不能只依赖 JDBC source `query` 的字段顺序或简单别名来表达映射关系。

系统必须生成明确的 SeaTunnel 数据链路：

1. `source` 节点读取源表字段，并通过 `result_table_name` 输出为临时源表。
2. `transform` 节点基于第 2 步最新映射关系生成字段转换结果。
3. `transform` 的输出字段名必须等于目标表字段名。
4. `sink` 节点必须通过 `source_table_name` 读取 `transform` 输出，而不是直接读取 `source` 输出。
5. 已有目标表场景下，`sink` 节点必须显式生成写入 SQL，SQL 中必须包含目标字段列表，不能只依赖 `generate_sink_sql = true` 的隐式字段推断。
6. 对于同名自动映射和手动异名映射，都必须进入同一个 transform 结果，确保实际运行、配置预览和用户看到的连线一致。

示例：

```hocon
source {
  Jdbc {
    result_table_name = "sync_source"
    query = "select `id`, `ajbh`, `ajmc` from `ajxx_tab`"
  }
}

transform {
  Sql {
    source_table_name = "sync_source"
    result_table_name = "sync_mapped"
    query = "select id, id as ajbh, ajbh as ajmc from sync_source"
  }
}

sink {
  Jdbc {
    source_table_name = "sync_mapped"
    query = "insert into public.a6 (id, ajbh, ajmc) values (?, ?, ?)"
    table = "public.a6"
  }
}
```

其中 `id as ajbh`、`ajbh as ajmc` 来自用户手动连线，不能被默认同名映射覆盖。
