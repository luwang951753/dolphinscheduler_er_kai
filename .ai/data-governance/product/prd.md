# 数据治理产品 PRD

## 1. 产品目标

在 DolphinScheduler 内提供一个轻量数据治理入口，解决用户在同步任务跑起来之后“资产在哪里、质量如何、血缘从哪来、问题谁处理”的管理问题。

第一版目标不是替代 OpenMetadata，而是在不引入复杂外部组件的前提下，实现一个可和现有数据预览、同步任务自然打通的治理工作台。

## 2. 用户故事

1. 作为数据开发，我希望看到所有已接入数据源中的表资产，方便快速定位数据。
2. 作为同步任务维护者，我希望看到源表到目标表的血缘，方便排查同步影响。
3. 作为平台管理员，我希望给表和字段配置标签、责任人，方便治理问题分派。
4. 作为数据负责人，我希望看到质量规则和异常问题，方便跟踪处理状态。

## 3. 信息架构

```text
数据治理
├── 首页
│   ├── 资产概览
│   ├── 质量概览
│   ├── 血缘概览
│   └── 待处理问题
├── 资产目录
│   ├── 筛选区
│   ├── 资产表格
│   └── 表格行内展开详情
├── 资产详情
│   ├── 概览
│   ├── 字段
│   ├── 质量
│   ├── 血缘
│   └── 问题
└── 质量与问题
    ├── 质量规则
    ├── 检测结果
    └── 治理问题
```

## 4. 首页设计

首页采用运营型后台仪表，不做大屏：

- 资产总数
- 有 Owner 资产占比
- 质量通过率
- 血缘关系数
- 待处理问题数
- 最近变更资产
- 最近失败质量检测

点击指标后进入资产目录或问题列表并带筛选条件。

## 5. 资产目录

资产目录采用高密度表格：

列：

- 资产名称
- 数据源
- 数据库 / Schema
- 类型
- 标签
- Owner
- 质量状态
- 最近同步任务
- 最近更新时间

筛选：

- 关键字
- 数据源类型
- 标签
- Owner
- 质量状态
- 是否有血缘

## 6. 资产详情

资产详情采用“表格行下方展开详情”的方式，不使用右侧窄详情面板。用户点击资产行后，当前表下方展开完整详情区，详情区横向空间更大，适合展示字段、质量规则、血缘和问题闭环。

展开区顶部只承担定位作用，不做属性看板。顶部展示资产名、完整路径、质量状态、标签和编辑元数据入口；Owner、字段数、最近检测、最近同步等低频属性放入“概览”Tab，减少详情展开后的首屏拥挤感。

详情包含：

- 概览：路径、说明、Owner、标签、最近同步任务、质量状态
- 字段：字段名、类型、注释、主键、可空、敏感标签
- 质量：规则、最近结果、异常数
- 血缘：上游、下游、同步任务关系
- 问题：待处理、处理中、已解决问题

## 7. 血缘设计

第一版血缘不做复杂图谱引擎，采用轻量左右节点布局：

```text
上游表  ->  当前表  ->  下游表
```

每条边显示：

- 来源：同步任务
- 最近运行状态
- 最近运行时间

血缘主视图归属“数据治理”。同步任务是血缘的生产方，保存或执行同步任务后沉淀 `源表 -> 目标表`；数据预览是血缘入口，只在当前表结构或预览页展示“查看血缘/查看治理资产”的轻量入口；数据治理是血缘的管理方，负责展示上下游、跳转资产、跳转同步任务和承接影响分析。

## 8. 数据质量设计

质量规则第一版作为资产详情内的模块：

- 非空
- 唯一
- 范围
- 枚举
- 正则
- 自定义 SQL

新建质量规则使用弹框，不离开当前资产上下文。弹框分为四块：

1. 基础信息：治理资产、规则名称、规则类型、规则层级、检测字段。
2. 规则条件：按规则类型展示不同参数，避免所有字段混在一起。
3. 执行与问题策略：检测范围、失败阈值、严重程度、检测频率、问题生成策略。
4. 规则预览与试运行：展示规则摘要、系统生成的检测 SQL、保存前校验、试运行结果。

检测 SQL 使用 Tab 展示，不和规则摘要堆在一起。SQL 内容拆成三段：

- 异常统计 SQL：统计 `abnormal_count` 和 `abnormal_rate`。
- 异常样本 SQL：受“样本保存”控制，保存前 50 条、前 200 条或不保存明细。
- 失败判定 SQL：受“失败阈值”控制，例如异常行数大于 0、异常率大于 1%、异常率大于 5%。

检测 SQL 不是只读展示，而是最终可编辑配置项。默认处于“系统生成”状态，规则类型、规则条件、范围条件、样本保存和失败阈值变化时自动刷新 SQL。用户在 SQL 编辑区手工修改后进入“手工编辑”状态，此时继续调整规则条件不会静默覆盖 SQL；只有点击“重新生成 SQL”才按当前表单条件覆盖回系统 SQL。

试运行和保存均以 SQL 编辑区的当前内容为准。系统需要做基础校验：禁止 `delete/update/insert/drop/truncate/alter` 等变更类语句，要求返回 `abnormal_count`；普通规则还要求保留失败判定 `check_result`，避免用户删除阈值判定后无法生成检测结果。

“范围条件”只有在检测范围选择“自定义 WHERE 条件”时可编辑；否则展示系统根据最近 1 天、最近 7 天生成的范围条件。

规则类型交互：

| 规则类型 | 层级 | 关键参数 | 业务含义 |
|----------|------|----------|----------|
| 非空校验 | 字段级 | 空值判断、异常样本保存 | 字段不能为空、空字符串或空格 |
| 唯一性校验 | 字段级 | 唯一键字段、重复处理口径 | 业务键不能重复 |
| 范围校验 | 字段级 | 最小值、最大值、边界包含、空值处理 | 数值字段必须在合理范围 |
| 枚举值校验 | 字段级 | 允许值、大小写规则、空值口径 | 状态/类型字段必须在合法集合 |
| 正则校验 | 字段级 | 正则表达式、空值处理、示例值 | 手机号、邮箱等格式检测 |
| 自定义 SQL | 表级 | 检测 SQL | SQL 必须返回 abnormal_count |

质量规则创建阶段不配置问题责任人。当前系统还没有完整人员分派体系，规则只负责发现问题；治理问题生成后再在问题闭环里处理责任归属。

质量规则保存后的展示位置必须明确：保存草稿或保存并启用后，弹框关闭并定位到当前资产详情的“质量”Tab。新规则展示在规则列表顶部，支持立即检测、历史结果、编辑和禁用。治理首页和资产目录只展示质量状态、异常数量和规则数量等摘要，不直接承担规则编辑。

保存草稿表示规则已记录但不参与自动检测；保存并启用表示规则进入待检测状态，后续可由手动检测、同步任务完成后检测或定时检测触发。

质量结果显示：

- 最近检测时间
- 通过 / 失败
- 异常行数
- 通过率
- 问题单状态

## 9. 视觉风格

- 对齐 Dolphin 现有后台风格。
- 借鉴 OpenMetadata 的资产目录和详情信息架构。
- 不使用复杂图表大屏。
- 不做营销式 Hero。
- 页面密度要适合长期运维和检索。

## 10. 成功标准

- 用户不用离开 Dolphin 就能看到数据资产和同步血缘。
- 用户能从数据预览或同步任务跳到治理详情。
- 用户能判断一张表是否可信：Owner、标签、质量状态、最近同步任务、问题状态。
