# 同步任务页面重构 PRD 选型

## 1. 背景

当前同步任务主流程已经跑通，但页面专业度和交互质感仍不足，尤其集中在三处：

1. 第 1 步“选择源与目标”更像普通表单，缺少成熟数据集成产品的上下文、校验、预览和引导。
2. 第 2 步“设计字段”的连线层视觉不稳定，左侧连线存在被字段面板遮挡的问题。
3. 第 3 步“执行与调度”的 DDL 需要用户手动点击生成，SQL 展示没有编辑器质感，也缺少高亮、格式化和状态表达。

本文件不直接替代正式 PRD，而是提供几套成熟产品参考下的重构方向，供确认后再合并进正式 PRD、交互文档和测试用例。

## 2. 成熟产品参考结论

| 产品 | 成熟做法 | 对同步任务的启发 |
|------|----------|------------------|
| DataWorks 数据集成 | Codeless UI 通过选择源端、目标端、通道、调度完成同步任务；高级参数集中在独立区域 | 第 1 步不应只是下拉框堆叠，应有源端/目标端上下文、连接状态、资源/调度预告 |
| Azure Data Factory Copy Data Tool | 按 Source、Destination、Advanced settings、Schedule、Review 组织；支持 schema capture、automatic mapping、filter data、scheduling | 当前 4 步合理，但第 1 步要更像“配置一条复制链路”，第 2 步要突出自动映射和少量手工修正 |
| Fivetran Schema Tab | 以 Schema / Table / Column 分层选择同步范围；表、列可启停；连接详情页有 Status、Schema、Usage、Setup 等分区 | 字段选择可以减少连线依赖，更多使用表格化 schema 配置和批量操作 |
| Airbyte Connection Setup | 连接建立后选择 streams 和 columns；字段选择决定目标表包含哪些列 | 第 2 步可以做成“字段目录 + 目标 schema”的结构，降低拖拽连线的使用频率 |
| AWS Glue Studio Visual ETL | Source、Transform、Target 以节点图表达；Change Schema 节点承担字段改名、类型转换、丢弃字段 | 如果要做强专业感，可以把同步任务表达成轻量 DAG，但实现成本更高 |
| DataGrip / CodeMirror 类 SQL 编辑器 | SQL 应该以编辑器方式呈现，具备高亮、行号、复制、格式化、只读/编辑状态 | 第 3 步 DDL 应自动生成，并以 SQL 编辑器区域展示，而不是普通 textarea |

## 3. 重构共同原则

无论选择哪套方案，都建议统一以下改造：

### 3.1 第 1 步：选择源与目标

- 不再采用“项目 + 源端 + 目标端”纵向表单堆叠。
- 改成左右对照的“源端卡片 / 目标端卡片”，中间展示同步方向。
- 每张卡片顶部展示数据源类型、连接名称、连接状态、当前选择路径。
- 数据源、数据库、表选择应支持搜索，不应只依赖长下拉。
- 选择源表后自动加载字段统计：字段数、主键、可空字段、样例行数或预览状态。
- 目标表名默认自动生成，但必须允许编辑。
- 目标端应展示建表策略：新建表 / 使用已有表 / 基于参考表。
- 下一步前显示配置校验摘要，而不是只靠表单必填红框。

### 3.2 第 2 步：设计字段

- 连线层必须独立于左右字段面板之上，避免被 `div` 裁切。
- 左右字段行高度保持一致，源字段锚点和目标字段锚点处于同一垂直中心。
- 默认映射不需要用户拖线，只有字段改绑时才使用拖拽。
- 连线应支持隐藏 / 显示切换。字段很多时，默认可只展示选中行或冲突行连线。
- 目标字段编辑应优先使用表格编辑体验，连线只是辅助理解映射关系。

### 3.3 第 3 步：执行与调度

- 进入第 3 步时自动生成 DDL，不再要求用户点击“生成建表语句”。
- DDL 区域改为 SQL 编辑器样式，至少包含：
  - SQL 语法高亮
  - 行号
  - 复制 SQL
  - 格式化
  - 重新生成
  - 编辑 / 只读状态
- DDL 自动生成后不自动执行，仍需用户点击“确认建表”。
- 建表状态应分为：未执行 / 建表中 / 成功 / 表已存在 / 失败。
- 调度配置不应挤在 DDL 下方，应以“立即执行 / 周期调度”分段或标签页展示。

## 4. 方案 A：DataWorks / Azure Copy Data 向导强化版

### 4.1 产品定位

保持当前四步向导，但把每一步做成专业数据集成产品的工作台。适合当前 Dolphin 二开，改造成本中等，最容易和现有实现对齐。

### 4.2 第 1 步页面

布局：

```text
顶部：同步任务名称 / 项目 / 当前校验状态

主体：
┌──────────────────────┐   ┌──────────────┐   ┌──────────────────────┐
│ 源端 Source           │ → │ 同步链路摘要  │ → │ 目标端 Target          │
│ 数据源：MySQL         │   │ 全量 / 单表    │   │ 数据源：PostgreSQL      │
│ 数据库：case_workbench│   │ 字段待加载     │   │ 数据库：test1           │
│ 表：ajxx_tab          │   │ DDL 待生成     │   │ Schema：public          │
│ 字段：10 / 主键：1    │   │ 调度未配置     │   │ 表：ajxx_tab_xxx        │
└──────────────────────┘   └──────────────┘   └──────────────────────┘

底部：连接校验 / 字段预取 / 下一步
```

核心交互：

- 先选项目，再选择源端和目标端。
- 源端选择完成后自动预取字段。
- 目标表策略默认“新建目标表”，可切换“使用已有表”或“基于参考表”。
- 中间链路摘要实时显示当前配置是否完整。
- 下一步按钮旁展示“已加载 10 个字段，可进入字段设计”。

### 4.3 第 2 步页面

- 保留左右字段面板 + 中间连线，但默认只显示已选字段连线。
- 连线层改成绝对定位 SVG 覆盖层，字段面板设置 `overflow: visible` 或将锚点放在面板外侧轨道。
- 字段表格上方提供“按名称自动映射 / 按顺序映射 / 清除映射 / 只看异常”。

### 4.4 第 3 步页面

- 进入页面自动调用 DDL 预览接口。
- 左侧是建表策略和状态，右侧是 SQL 编辑器。
- SQL 编辑器默认可编辑，修改后出现“已手工修改”标识。
- 点击“重新生成”时提示是否覆盖手工修改。

### 4.5 优点

- 和当前四步结构最兼容。
- 用户学习成本低。
- 最符合 DataWorks / Azure Copy Data 的成熟同步任务心智。
- 重构风险可控。

### 4.6 缺点

- 专业感提升明显，但不会像 AWS Glue 那样有强视觉画布感。
- 第二步仍保留连线，需要修复连线层和字段行对齐。

### 4.7 推荐程度

推荐作为首选方案。

## 5. 方案 B：Fivetran / Airbyte Schema 配置版

### 5.1 产品定位

把同步任务弱化为“连接 + Schema 选择 + 运行策略”，减少复杂连线，让用户像管理同步连接一样管理表和字段。

### 5.2 第 1 步页面

布局：

```text
顶部：新建同步连接

左侧：连接选择
- 源连接
- 目标连接
- 项目
- 同步频率

右侧：Schema Discovery
- 源库 / 表树
- 目标 schema
- 当前表字段概览
- 连接测试结果
```

核心交互：

- 选择源端后自动做 schema discovery。
- 用户在右侧树中选表。
- 选择表后展示字段列表、主键、类型、注释。
- 目标端只配置目标 schema 和命名策略，不强迫一开始填很多细节。

### 5.3 第 2 步页面

- 用 schema 表格管理字段启停。
- 字段行支持启用 / 禁用、目标名、目标类型、注释、主键、可空。
- 默认按名称映射，不强调连线。
- 仅在“高级映射”模式下展示连线。

### 5.4 第 3 步页面

- DDL 自动生成，展示为“Destination Schema Changes”。
- 以变更清单 + SQL 编辑器双视图呈现：
  - 新建表
  - 新增列
  - 修改类型
  - 主键变化

### 5.5 优点

- 字段多时比连线更稳。
- 更适合后续扩展多表同步。
- 页面更像成熟 ELT 产品。

### 5.6 缺点

- 当前用户已经习惯四步向导，切换到连接详情式体验会有一点认知变化。
- Dolphin 工作流保存、调度的概念需要额外放进页面，不如方案 A 自然。

### 5.7 推荐程度

适合后续做多表同步或长期产品化；当前单表同步阶段可部分借鉴。

## 6. 方案 C：AWS Glue Studio 轻量 DAG 版

### 6.1 产品定位

把同步任务表达成可视化 DAG：Source -> Change Schema -> Target -> Schedule/Run。适合强调专业感和可扩展转换能力。

### 6.2 第 1 步页面

布局：

```text
顶部工具条：保存 / 运行 / 调度 / 配置预览

主体画布：
[MySQL Source] -> [Change Schema] -> [PostgreSQL Target]

右侧属性面板：
选中 Source 时配置源端
选中 Target 时配置目标端
选中 Change Schema 时配置字段映射
```

核心交互：

- 默认画布已有三个节点。
- 用户点击 Source 节点配置源数据源、库、表。
- 用户点击 Target 节点配置目标数据源、库、schema、表策略。
- 节点下方显示校验状态。

### 6.3 第 2 步页面

- 不再是独立步骤，而是点击 Change Schema 节点进入字段映射面板。
- 字段映射以表格为主，连线为可选视图。
- 支持未来增加 Filter、Derived Column、Lookup 等节点。

### 6.4 第 3 步页面

- 点击 Target 节点查看自动生成 DDL。
- SQL 编辑器作为 Target 节点的 Schema Preview 标签。
- 调度作为画布级右侧面板。

### 6.5 优点

- 专业感最强。
- 后续扩展转换、过滤、Lookup、质量校验很自然。
- 和 AWS Glue Studio 的视觉 ETL 心智接近。

### 6.6 缺点

- 对当前单表同步是偏重的方案。
- 改造成本最高。
- Dolphin 本身已有工作流 DAG，页面内再放一个 DAG 可能和原生工作流概念重叠。

### 6.7 推荐程度

不建议当前立即采用，除非明确要把同步任务升级为完整可视化 ETL 设计器。

## 7. 方案 D：混合推荐版（DataWorks 向导 + Airbyte Schema + DataGrip SQL）

### 7.1 产品定位

保留当前四步向导的大结构，但按成熟产品分别优化各步骤：

- 第 1 步采用 DataWorks / Azure Copy Data 的源目标对照式向导。
- 第 2 步采用 Airbyte / Fivetran 的字段表格配置为主，连线只作为高级映射辅助。
- 第 3 步采用 DataGrip / CodeMirror 风格 SQL 编辑器，DDL 自动生成并高亮。

这是最适合当前 Dolphin 二开阶段的折中方案。

### 7.2 第 1 步详细 PRD

页面标题：选择源与目标

页面目标：让用户在一个屏幕内明确“从哪个表同步到哪个表”，并在进入字段设计前完成连接可用性和字段预取。

信息架构：

| 区域 | 内容 | 交互 |
|------|------|------|
| 顶部任务栏 | 项目、任务名称、配置状态 | 项目必选；任务名默认根据源目标生成 |
| 源端卡片 | 数据源、数据库、表、字段统计、连接状态 | 每项支持搜索选择；选择表后自动加载字段 |
| 目标端卡片 | 数据源、数据库、schema、目标表策略、目标表名、参考表 | 目标表名自动建议；策略影响第 3 步 DDL |
| 中间摘要 | 同步方向、字段加载状态、DDL 策略、调度状态 | 实时更新，错误项可点击定位 |
| 底部校验条 | 已完成项、缺失项、下一步条件 | 校验通过后下一步可用 |

关键交互：

1. 选择源数据源后，源数据库、源表、源字段清空。
2. 选择源数据库后，源表和源字段清空。
3. 选择源表后，自动加载字段元数据，并自动推荐目标表名。
4. 选择目标数据源后，目标数据库、schema、参考表清空。
5. 选择目标库后，默认 schema 为 `public` 或后端返回的默认 schema。
6. 用户切换目标表策略：
   - 新建表：第 3 步自动生成 `CREATE TABLE`。
   - 使用已有表：第 3 步展示目标表字段对比，不默认建表。
   - 基于参考表：第 2 步目标字段默认参考该表。
7. 下一步前展示校验摘要：
   - 项目已选择
   - 源端连接可用
   - 源表字段已加载
   - 目标端连接可用
   - 目标表策略已确认

### 7.3 第 2 步详细 PRD

页面标题：设计字段

页面目标：让用户优先通过表格完成字段选择、目标字段编辑和映射确认；连线只解决“看关系”和“改绑”。

布局：

```text
左：源字段表格       中：映射轨道        右：目标字段表格
字段名/类型/注释     连线 SVG 层        目标名/类型/注释/主键/可空/来源
```

关键改造：

- 连线 SVG 层放在左右字段面板之上的独立绝对定位层。
- 左右字段列表滚动时，连线根据字段行 DOM 位置重新计算。
- 源字段锚点放在左表格右外侧 8px，不放在会被裁切的单元格内部。
- 目标字段锚点放在右表格左外侧 8px。
- 字段面板需要允许锚点区域可见，或预留映射轨道宽度。
- 默认只展示已选字段映射线。
- 提供“隐藏连线 / 显示连线 / 只看异常”切换。
- 字段较多时优先保证表格编辑，不让连线造成视觉噪音。

### 7.4 第 3 步详细 PRD

页面标题：执行与调度

页面目标：让用户进入该步骤后立即看到系统生成的 DDL，并能用专业 SQL 编辑器检查、复制、格式化、确认建表，再配置执行方式。

布局：

```text
左侧：执行策略
- 目标表策略
- 建表状态
- 立即执行 / 周期调度
- 资源组 / Worker 组

右侧：DDL SQL 编辑器
- 自动生成中 / 已生成 / 已手工修改
- SQL 高亮 + 行号
- 复制 SQL / 格式化 / 重新生成
- 确认建表
```

关键交互：

1. 进入第 3 步自动调用 DDL 预览接口。
2. 加载期间显示 SQL 编辑器骨架和“正在根据字段映射生成 DDL”。
3. 生成成功后展示高亮 SQL。
4. 用户编辑 SQL 后标记为“已手工修改”。
5. 点击“重新生成”时：
   - 若未手工修改，直接覆盖。
   - 若已手工修改，二次确认是否覆盖。
6. 点击“确认建表”后才调用建表接口。
7. 建表成功后状态变为“已建表”，失败则展示后端错误和重试按钮。
8. 复制 SQL 不依赖确认建表，随时可用。

### 7.5 推荐程度

强烈推荐。它保留当前项目已有基础，又能明显提升成熟度和专业感。

## 8. 选择建议

| 判断维度 | 方案 A | 方案 B | 方案 C | 方案 D |
|----------|--------|--------|--------|--------|
| 当前代码改造成本 | 中 | 中高 | 高 | 中 |
| 页面专业感提升 | 高 | 高 | 最高 | 高 |
| 用户学习成本 | 低 | 中 | 高 | 低 |
| 适配 Dolphin 四步向导 | 高 | 中 | 低 | 高 |
| 适合单表同步 | 高 | 中 | 中 | 高 |
| 适合未来多表同步 | 中 | 高 | 高 | 中高 |
| 推荐优先级 | 2 | 3 | 4 | 1 |

建议先选方案 D。若后续确认要做多表批量同步，再吸收方案 B 的 Schema Tab 思路；若未来要做字段转换、过滤、Lookup、质量校验等复杂编排，再评估方案 C。

## 9. 待确认问题

1. 第 1 步是否允许增加“任务名称”输入？如果允许，默认按源目标自动生成，用户可改。
2. 目标表策略是否先做三种：新建表、使用已有表、基于参考表？
3. 第 2 步是否接受“表格编辑为主，连线为辅助”，而不是强依赖连线？
4. 第 3 步 SQL 编辑器是否可以引入前端编辑器依赖，例如 CodeMirror 或 Monaco？
5. 周期调度是否本轮只优化入口和展示，暂不重做 Dolphin 原生定时逻辑？
